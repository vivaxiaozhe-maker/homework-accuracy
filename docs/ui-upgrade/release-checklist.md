## 1. 授权门禁

| 动作 | 当前授权状态 | 后续要求 |
|---|---|---|
| 本地/隔离环境实施与测试 | 已批准按计划进行 | 只用合成数据，不触发真实家长通知 |
| Git commit / push | 本任务未授权、未执行 | 审阅 diff 后分别请求明确授权；不得用 `git add -A` 卷入其他改动 |
| 生产备份与发布 | **未授权** | 发布前单独确认时间窗、执行人、目标版本与回滚负责人 |
| 生产数据清理/导入/修复 | **未授权** | 不在 UI 升级中附带执行；测试 fixture 禁止导入生产 |
| 真实微信、二维码、PDF 外部链路 | **未授权** | 仅在授权测试环境和测试接收人范围验证 |

任何一步勾选都必须附实际时间、执行人、命令/结果和证据路径；文档中的建议命令不代表已经运行。

## 4. 未来部署顺序（后端先于前端）

新事务接口是前端新流程的前置能力，因此采用“先兼容后端、再前端”的顺序；不得先发会调用不存在接口的新前端。

1. [ ] `NOT_RUN` 进入已确认的维护窗口，冻结发布期间其他文件修改和写入；再次核对备份可用。
2. [ ] `NOT_RUN` 发布后端代码，按本次锁文件执行 `npm ci`（使用受控 npm cache），不手改锁文件、不混入未审阅依赖。
3. [ ] `NOT_RUN` 用受控 pm2 配置重启 `xueqing`；不输出或复制密钥。检查启动日志、DB 打开、附件目录和 `/api/health` 的 `{ok:true,app:'xueqing-api'}`。
4. [ ] `NOT_RUN` 用旧前端做兼容冒烟：登录、state、原 records/missed、计划、报告读取、附件读取；验证新后端未破坏旧调用。
5. [ ] `NOT_RUN` 仅在隔离/授权测试范围验证新 R01/R02 接口，包括失败回滚与重试；不向真实家长发送消息。
6. [ ] `NOT_RUN` 由既有同步逻辑生成 `index.html/dist/index.html`，再发布前端静态文件；保留 CSP、静态白名单和 no-store。
7. [ ] `NOT_RUN` 验证线上静态版本号、classic script 顺序和实际加载资源；强制刷新后仍为新版本。
8. [ ] `NOT_RUN` 先做不发送真实通知的三角色只读检查，再按授权范围做写入验证；分别记录保存结果和推送结果。
9. [ ] `NOT_RUN` 观察错误日志、会话、API 4xx/5xx、附件和报告 H5；确认稳定后结束维护窗口并归档证据。

`deploy.sh` 链包含同步、smoke、git push、scp 和线上验证；未获 Git/生产授权前不得运行。若使用它执行未来发布，也必须先确认其步骤与本次审批范围一致。

## 5. 回滚顺序（与部署反向）

触发严重越权、数据不一致、事务部分成功、关键链路不可用或无法解释的版本异常时，停止扩大验证并启动回滚。

1. [ ] `NOT_RUN` 记录触发时间、现象、日志和当前版本；停止新前端写入，保留现场，不清数据“修复”。
2. [ ] `NOT_RUN` 先回滚前端到上一已验证静态版本，避免旧后端恢复前继续调用新接口；验证版本号和关键只读链路。
3. [ ] `NOT_RUN` 再回滚后端代码，按旧锁文件 `npm ci` 并用旧受控配置重启 pm2；检查 health 和原 API。
4. [ ] `NOT_RUN` 若本轮确无 schema/数据迁移，通常不覆盖数据库；保留回滚期间新数据，并核对新接口已产生的记录/审计。
5. [ ] `NOT_RUN` 若后续存在 schema 或数据迁移，只能执行预先演练的对应回滚方案。不得直接用旧备份覆盖回滚期间的新生产数据；需由负责人评估数据合并/前滚。
6. [ ] `NOT_RUN` 附件按同一备份/变更清单恢复或前滚，避免 DB 与 files 磁盘状态错配；不得批量删除无法立即判定归属的文件。
7. [ ] `NOT_RUN` 做旧版本三角色关键链路、权限、记录/未交、附件和报告只读验证，确认服务稳定。
8. [ ] `NOT_RUN` 汇总影响范围、数据差异、回滚证据与后续修复计划；重新发布需要新的明确授权。
